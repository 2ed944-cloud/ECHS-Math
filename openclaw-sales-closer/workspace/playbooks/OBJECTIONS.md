# Objection library

Use: acknowledge → diagnose → answer → verify.

## “We already use another platform.”
Diagnose whether the issue is replacement or fragmentation.
Answer:
“That may be a reason not to replace it. The useful question is whether your current stack already gives you a connected lesson-to-practice-to-recovery-to-teacher-evidence workflow. If it does, we should not create unnecessary change.”
Then ask what is missing.

## “Teachers will not use another tool.”
Ask what caused prior adoption failure.
Focus demo on the smallest teacher workflow.
Do not promise adoption percentages.

## “The price is high.”
Do not discount first.
Ask:
“High relative to which alternative: current software cost, teacher preparation time, or the expected outcome?”
Re-anchor scope/value, then use only pricing authority in `pricing.json`.

## “Can you prove it improves exam results?”
Answer:
“I don’t have a verified causal outcome study in the current sales evidence, so I would not claim a percentage improvement. What I can demonstrate is the learning workflow and evidence system, and we can define success metrics for a pilot.”

## “Is it officially College Board / IB approved?”
Answer:
“I should be precise: I do not have a verified endorsement or partnership record that allows me to say that. The reference implementation includes AP/IB mathematics course pathways; exact licensing and curriculum claims should be treated separately.”

## “Is it secure / compliant?”
Answer:
“The current repository includes role-based server operations, session-token hashing and audit logging. I won’t claim a certification we have not independently verified. Tell me your vendor-security checklist and I’ll separate what is evidenced from what requires review.”

## “We need SSO / LMS integration.”
Do not invent.
Capture required integration and mark technical verification.

## “We want custom features.”
Determine if it is essential.
Never quote timeline/price for custom development unless configured.

## “Send us a proposal.”
Before sending, confirm:
- users/scope;
- courses;
- term;
- implementation need;
- commercial contact;
- decision date.
A proposal without these is usually premature.

## “We need a free trial.”
Use only the configured pilot policy. Never create an unlimited custom pilot on the fly.
