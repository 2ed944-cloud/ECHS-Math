## Architectural addition

Migration `202609080002_lesson_persistence.sql` adds four tables: `authored_lessons`, `lesson_versions`, `lesson_reviews`, and `lesson_publications`. One new Edge Function, `lesson-api`, mediates all access through the existing opaque school-session token. The migration count becomes 22 and the Edge Function count becomes 12; the dated ECHS-001 inventory remains a historical baseline.

Existing HTML lessons, catalog URLs, curriculum definitions, question providers, authentication, learning evidence, and publication gates are unchanged. No current page loads the institutional renderer automatically. No production classes are pinned or lessons seeded by this migration. The optional loader is enabled explicitly by a later route integration.

The database uses ECHS account UUIDs, hashed session tokens and organizational/class membership, not Supabase `auth.uid()`. Edge performs an initial session lookup and role check. Every subsequent `lesson_store` RPC checks session, active account, organization, class, membership, course pin and operation again inside its transaction. Authorization cannot be supplied through client actor/organization fields.

## Permissions and storage

Direct table privileges, including TRUNCATE, are revoked from PUBLIC, anon, authenticated and service_role. RLS is enabled without permissive client policies. Only service_role can execute the two public lesson RPCs. Definer functions fix `search_path=pg_catalog` and qualify database objects; helper functions are private and not executable by those application roles. The service credential remains an Edge environment secret.

Teachers need a teacher membership in the exact active class, with an active account in the same organization. Administrators operate inside their organization. Students can only request a current published document in an assigned class. Parents cannot access lesson authoring or this delivery API. Invisible resources return a generic 404; internal SQL details are never returned.

Class course versions must first be explicitly pinned by an administrator. Pin replacement locks the class, compares the expected current assignment, and supersedes/inserts atomically. Only active, compatible, non-placeholder course versions are eligible. This uses the existing ECHS-003 authoritative curriculum snapshot; it introduces no new AP/IB objectives or changes to current cohort behavior. Future IB first-assessment-2029 remains ineligible.

An authored lesson is bound permanently to its organization, class, course version, catalog access key, route, unit/topic and slug. Catalog mappings use `legacy:<course-family>:unit:<one-based-unit>` and a safe legacy topic identifier; unsuitable topic text uses a SHA-256 identifier while retaining the original literal for legacy progress lookup. These are provenance mappings to existing catalog rows, not claims of official curriculum-objective alignment.

## Lifecycle and conflicts

Create starts at revision 1. Save and restore append immutable snapshots; restore never overwrites an earlier version. A lesson's `head_revision` changes on every workflow mutation. The client must supply its last observed revision; a stale writer receives 409 and must reload. Document version numbers may have gaps because review/publication actions also consume revisions.

Review requires an explicit request followed by approval from a different authorized staff account than both the lesson creator and current version creator. Approval includes affirmative curriculum, mathematics, accessibility, rights and student-safety checks plus an API review comment. These are accountable human review declarations, not proof generated by an automated validator.

Before approval/publication, Edge validates the exact immutable stored head with the canonical schema, semantic checks and pinned KaTeX 0.16.27. It passes that version ID itself to SQL. SQL repeats authority, expected-revision, exact-head and review-state checks under locks. Publish appends an immutable institutional snapshot, with the original source document version and a new publication revision. New drafts leave the previous publication live. Unpublish appends a withdrawal event and clears the current publication pointer; it does not remove history.

Private teacher notes are a separate bounded field on private versions. The student response is an explicit projection: document, publication identifiers/revision and account/class/course/route binding. Notes, staff heads, reviews and history never enter it. Putting sensitive prose directly in a student content block still requires human review to prevent disclosure; the schema cannot classify the meaning of ordinary text.

Student delivery also checks the existing class-specific release rules: ready catalog item; hidden/shown override; the first two positions; or completed lesson plus completed, nonempty practice for the preceding ready item. Membership, current course pin, session, catalog and visibility changes are protected by transactional locks. No cross-class override grants access. Existing unversioned completion/practice records remain a compatibility input only: this work neither writes mastery nor claims those historic records distinguish AB/BC versions.

## API contract

Base: `/functions/v1/lesson-api`. Authenticated requests use `Authorization: Bearer <existing ECHS school token>`. POST bodies are strict JSON; unknown fields, duplicate queries, actor overrides and stale revisions are rejected. Exact allowed origins are configured by the existing backend deployment. Responses are `no-store, private`.

| Method and path | Operation |
| --- | --- |
| GET `/health` | Public readiness boolean and contract name only |
| GET `/context?class_id=<optional UUID>` | Authorized staff class/pin/catalog context |
| POST `/classes/:id/course-version` | Admin pin with `course_version_id`, `expected_assignment_id` (UUID or null), `reason` |
| GET `/lessons?class_id=...` | Staff lesson metadata |
| POST `/lessons` | Create with class/course/access key, canonical document, private notes, expected revision 0 |
| GET `/lessons/:id` | Staff current draft and bounded recent metadata |
| GET `/lessons/:id/history?limit=...&before_version=...` | Paginated version metadata, without notes/content |
| GET `/lessons/:id/versions/:versionId` | Staff immutable version and private notes |
| POST `/lessons/:id/draft` | Save `document`, `private_notes`, `expected_revision` |
| POST `/lessons/:id/restore` | Restore `version_id` with expected revision |
| POST `/lessons/:id/request-review` | Request review at expected revision |
| POST `/lessons/:id/approve` | Independent review: checks, comment and expected revision |
| POST `/lessons/:id/publish` | Publish approved head at expected revision |
| POST `/lessons/:id/unpublish` | Withdraw with reason and expected revision |
| GET `/lessons/:id/published?class_id=...` | Authorized immutable student-safe snapshot and binding |

Persisted documents have a separate 1 MiB compact JSON UTF-8 budget. The general canonical schema's larger budget is unchanged. Edge checks projected save/restore/publication snapshots too, including revision digit growth. SQL has a secondary 2 MiB JSONB text cap to accommodate PostgreSQL whitespace. HTTP bodies are capped at 1 MiB + 128 KiB and 10 seconds; RPC requests time out after 15 seconds with no automatic mutation retry. Private notes allow 20,000 characters. History is bounded to 100 entries/request. No raw HTML, scripts, answer fields, or arbitrary remote endpoints are introduced. Legacy embedded references may remain in drafts but cannot be approved, published or delivered until a future trusted importer verifies their provenance.

## Renderer integration contract

`mountInstitutionalLesson({root, lessonId, classId, enabled: true, window, mathEngine})` in `js/lesson-runtime/renderer.mjs` captures the current institutional account/session, resolves the configured fixed Supabase endpoint, fetches the authorized publication itself, validates its exact identity/route binding, and then uses the existing access and finish/practice integration. Callers cannot inject a fetched private document or skip the public renderer's audience checks. Default `enabled: false` performs no network or DOM changes.

Account/token changes, stale requests, disposal, remounting and route changes fail closed. Requests and response bodies are bounded, redirects are refused, and credentials are not sent to an arbitrary endpoint. Math, keyboard navigation, responsive layout and deep links retain the existing rendering behavior. The loader does not persist content, write progress or award mastery.

Run in a clean checkout with pinned dependencies installed as in the workflows:


The database workflow creates a disposable PostgreSQL 15 service, installs pinned psycopg 3.2.9, then executes all 22 migrations and `tools/test_lesson_persistence_database.py`. `ECHS_LESSON_TEST_DSN` must explicitly name a loopback database prefixed `echs_lesson_test`; production connection discovery is forbidden. The harness tests role/RLS/scope, immutable history, workflow, release prerequisites and real concurrent revision/revocation races. Static-only mode is not an acceptance result.

After that migration test, `node tools/test_lesson_persistence_e2e.mjs` exercises the actual Request/Response handler, pinned math engine and real session-authenticated SQL using a parameterized test-only Python stdio bridge. This closes the HTTP/SQL response-shape gap; it is not a test of the production PostgREST network. Transport behavior has separate unit tests. Disposable fixture accounts/tokens/data are not production accounts, and the test tools are excluded from Pages.

## Deployment and rollback

Use the existing backend deployment after a reviewed, passing merge. It applies the additive migration, deploys all institutional functions, checks the new lesson health endpoint and runs existing production login/session diagnostics. Pages retains its existing release builder, public-source exclusions and URLs. Do not copy database documents, staff notes, test fixture data or service secrets into public assets.

Rollback order: keep existing routes on their unchanged legacy renderer; disable any later institutional-loader feature flag; revert the Edge/loader integration to the last validated version if necessary. Preserve immutable database rows and migration history. The additive schema can remain dormant; do not drop tables or reverse a migration against live authored content. Re-enabling must revalidate the active course pin, publication, membership and route. Existing question publication/release controls and mastery rules remain mandatory.

Unresolved scope: authoring UI, current-route cutover, verified legacy imports, media/question blocks, a content-difference UI, automatic rights verification and version-aware learning evidence belong to later tasks. ECHS-008 can start only after the validation and production acceptance record is complete.
