PostgreSQL, HTTP, owner adoption and hosted execution have not run. The active27 migrations, all three cloud writers and the sealed transport release remain unchanged.

The slice protects the existing six learning tables after a synthetic database-owner adoption. Existing score/trust guards remain installed with their original definitions and grants. An owner route is not grading authority.

## Private metadata and lock design

`learning_owner_fences` provisions one live fence for each existing account and transactionally for future account creation. Its immutable incarnation UUID and initial organization/account identifiers contain no learning payload, personal name or token. The live account reference is a globally unique account FK. It deliberately permits an unadopted account to move organizations without adding a new composite-FK restriction.

The fence begins at epoch0. Adoption changes the epoch to1 in a nonpartial unique key. Each legacy INSERT, UPDATE or DELETE locks the applicable OLD and NEW owner fences with `FOR KEY SHARE`, using ordered owner identifiers. An adopted fence raises55000. A missing fence raises40001, including a higher-isolation snapshot that predates account provisioning. A snapshot predating installation cannot silently infer that a missing companion means legacy mode. Such concurrent migration/provisioning cases may require transaction retry; this candidate does not claim their behavior is unchanged.

The adopted route references the current organization/account and the exact fence version. Account deletion, account-ID mutation and organization moves for an adopted owner are deliberately restricted. Route updates/deletion and epoch reset are prohibited. All three private tables use RLS and revoke table access from PUBLIC, anon, authenticated and service_role; all eight trigger functions revoke direct execution from those roles. The database/schema owner remains trusted.

For never-adopted account deletion, the live FK uses SET NULL and leaves a private metadata tombstone. Its uniqueness is a partial index so reference clearing should remain a non-key update, compatible with outstanding legacy key-share locks. Reusing a deleted account UUID creates a new incarnation; it cannot acquire an old fence's adoption state. The current candidate retains unadopted tombstones indefinitely. Later retention maintenance must be reviewed separately; live or adopted fences cannot be deleted. Organization deletion and empty account-ID mutation have explicit regression cases. Direct whole-table private TRUNCATE remains prohibited even at zero adoption.

Adoption locks the six legacy relations in ACCESS SHARE mode, then a singleton barrier, organization, account and owner fence. This permits ordinary legacy DML and serializes TRUNCATE. Adoption updates the singleton's nonpartial unique epoch key. A TRUNCATE trigger key-locks that singleton and rejects any adoption; the singleton is necessary because a fixed snapshot can miss an entirely new account and route. All-six legacy TRUNCATE remains possible while adoption is zero. Once any owner is adopted, global TRUNCATE is deliberately denied. Operations spanning several tables can still encounter PostgreSQL's ordinary transaction deadlock/serialization rules; only the stated race orders are tested here.

These lock assumptions follow PostgreSQL15's documented key-lock and unique-index rules, but documentation is not execution evidence. The suite must prove the actual epoch conflict, SET NULL lock compatibility, both race orders, fixed-snapshot failures, cascade behavior and rollback. See [PostgreSQL15 locking](https://www.postgresql.org/docs/15/explicit-locking.html) and [transaction isolation](https://www.postgresql.org/docs/15/transaction-iso.html).

## Harness

Run offline guards with `python test_local.py`, or source-only validation with `python run_integration.py`. The default runner does not import a database driver. Offline results explicitly say PostgreSQL was not executed.

Actual execution requires the pinned `psycopg[binary]==3.2.9` driver and a new isolated PostgreSQL15 cluster. Set only the two explicit test DSNs; ambient `PG*` variables are refused. Both DSNs must specify the same credentials/loopback host/port, with distinct database names under `echs_membership_test_owner_fence_` and `echs_bank_test_owner_fence_`. The membership DB must exist and be empty; the bank DB and four fixture roles must not exist. The runner creates the bank DB, never deletes or resets one, and retains diagnostics on failure. Use `python run_integration.py --execute` only in that disposable environment.

The runner executes unchanged membership55 against the prior26 chain first. It then runs the unchanged archive222 suite on the exact27 prefix in a second database. A transparent test-only `psycopg.Connection` subclass executes candidate SQL exactly once immediately after the pinned migration003 statement; no SQL call, result or assertion is mocked, skipped or rewritten. The original archive report continues to describe its27 source migrations; the separate outer report explicitly binds the additional candidate and insertion point. Installation compares every public-row hash and existing table grants/RLS, function definitions/grants and trigger definitions before/after. Candidate tests then exercise all six tables, service roles, OLD/NEW ownership, bulk rollback, duplicate upserts, cascade/incarnation rules and independently connected concurrency.

The outer report becomes an actual-PostgreSQL pass only after all baseline and candidate assertions complete and sources are rehashed. Local source hashes, compilation or simulated connection-object checks cannot satisfy that status.

## Remaining boundaries

The three existing writers authenticate in HTTP and issue separate PostgREST statements. Their table writes carry no current custom-session token into these triggers. This slice therefore cannot revalidate expiry after a legacy statement waits, cannot make several legacy HTTP calls atomic, and adds no such claim. A future adopted-owner journal RPC must revalidate session/tenant after serialization, store immutable intent and provide exact replay/CAS receipts before any real adoption.

The reader/queue/reset/old-tab closure and approved server baseline adoption are still required by the parent implementation plan. No learner is automatically adopted on login, migration, page load or a request header. Rollback before adoption can remove this isolated proposal; rollback after adoption cannot delete routing metadata and reopen old writers. It must preserve both histories and use a separately reviewed reconciliation.
